# Zigbox 0.6.0

0.6.0 ships S2, **lazy start**: `zbx run --lazy` starts a container from a registry image before
the image is local, fetching each file's chunks as the container reads them and the rest in the
background. It is the first public preview of Zigbox and Zigcube together
([decision](../decisions/2026-11-16-0.6.0-first-public-preview.md),
[plan](../decisions/2026-11-19-0.6.0-plan.md)). `--lazy` stays opt-in and experimental: `zbx run`
without it is unchanged. It stays a public beta for **Debian and Fedora only** (the apt and dnf
repositories on zigbox.org, x86_64 and aarch64), as 0.5.1 to 0.5.3 were.

Three other changes matter to everyone who installed an earlier release:

- **The release signing key is new.** Every package, repository and `SHA256SUMS` of 0.6.0 is
  signed by a new key; apt and dnf refuse 0.6.0 until you replace the old key. The steps are in
  [The new release key](#the-new-release-key) below.
- **Push and export write new digests.** `zbx push` and `zbx store export` write layer writer 2,
  so the same tree gets different layer and manifest digests from 0.5.x
  ([Upgrading](#upgrading)).
- **The project moved** from `github.com/Zigbox` to `github.com/ZigboxOrg`, and Zigbox is now
  **Apache-2.0** (0.3.0 to 0.5.3 shipped under MIT).

The history of `main` was restarted when the project moved, so v0.5.3 is not an ancestor of the
0.6.0 commit: 0.6.0 is the tree diff `v0.5.3..main`, which is pull requests #1 to #18 of
`ZigboxOrg/zigbox` and S2 slices 5 and 6.

## Scope: Debian and Fedora

Unchanged from [0.5.1](0.5.1.md): the packages are built, signed and checked for Debian (apt) and
Fedora (dnf), and those are the installs this beta supports. Other Linux distributions may run the
static `zbx` from the release tarballs, untested and unsupported. The Mac build ships through the
Homebrew tap, outside this beta's support; `zbx run --lazy` on the Mac is not part of 0.6.0.

## The new release key

The previous primary key's secret half was lost in the move to `ZigboxOrg`, so the release key
was replaced on 2026-11-20 ([decision](../decisions/2026-11-20-release-key-rotated.md)):

| Key | Fingerprint |
| --- | --- |
| Old primary (retired, no longer used) | `09991DC39816D3C914E2A22C5AB00BC328B7DBB7` |
| New primary (RSA 4096, certify-only, "Zigbox releases <releases@zigbox.org>") | `1207CB8600CE25FFDD3CC87ECCBEC141C3348787` |
| New signing subkey (RSA 4096, expires 2027-11-20) | `4A1D7E3AD844177A496A072EC07B2441C39645B7` |

The public key is checked in as [zigbox-release-key.asc](zigbox-release-key.asc) (sha256
`fcc3a9aeaeb47da1683ea20ba12cd33e91a95ef040bd09893b7f5f4399c2ae53`). zigbox.org serves it as
`https://zigbox.org/zigbox-archive-keyring.gpg` and `.asc` from this release on; before 0.6.0 was
published those URLs served the old key, so the fingerprint checks below fail if run earlier.

**The old key is not used again**, for packages, repository metadata or `SHA256SUMS`. It is not
revoked (no revocation certificate is known to survive), so it stays valid in keyrings that hold
it; that is harmless while nobody can sign with it, and it is why you replace the old key rather
than add the new one beside it. A machine that holds only the old key refuses 0.6.0: apt fails
`apt update` with `NO_PUBKEY C07B2441C39645B7` (the new subkey's long id; it may also say
`EXPKEYSIG` or `BADSIG`), and dnf or rpm refuses the signature.

Each block downloads to a temporary file, checks that it holds exactly one key with the new
primary fingerprint, and only then installs it; if the check fails, nothing is installed.

**apt (Debian, Ubuntu)**, replacing the file the install guide wrote:

```sh
f=$(mktemp) && curl -fsSLo "$f" https://zigbox.org/zigbox-archive-keyring.gpg
test "$(gpg --show-keys --with-colons "$f" | awk -F: '$1=="pub"{n++;w=1} $1=="fpr"&&w{print $10;w=0} END{if(n!=1)print "BAD"}')" = 1207CB8600CE25FFDD3CC87ECCBEC141C3348787 \
  && sudo install -m 0644 "$f" /usr/share/keyrings/zigbox.gpg && echo installed
rm -f "$f"
sudo apt update
```

**dnf (Fedora, Rocky, RHEL)**:

```sh
f=$(mktemp) && curl -fsSLo "$f" https://zigbox.org/zigbox-archive-keyring.asc
test "$(gpg --show-keys --with-colons "$f" | awk -F: '$1=="pub"{n++;w=1} $1=="fpr"&&w{print $10;w=0} END{if(n!=1)print "BAD"}')" = 1207CB8600CE25FFDD3CC87ECCBEC141C3348787 \
  && sudo rpm --import "$f" && echo imported
rm -f "$f"
```

Then remove the old key from rpm and refresh:

```sh
sudo rpm -e gpg-pubkey-28b7dbb7
sudo dnf clean metadata && sudo dnf makecache
```

`rpm -qa 'gpg-pubkey*'` lists the old key's entry as `gpg-pubkey-28b7dbb7-*`; use the full name
that listing prints if rpm says the short one is ambiguous. Skipping the `rpm -e` is harmless, but
the old key then stays trusted by rpm. If dnf asks to import the repository key itself
(`repo_gpgcheck=1`), compare the fingerprint it prints with
`1207 CB86 00CE 25FF DD3C C87E CCBE C141 C334 8787` and do not use `-y` for that first import (not
yet checked on a dnf 4 host).

**Release tarballs.** Download `zbx-0.6.0-linux-<arch>.tar.gz` (`x86_64` or `aarch64`),
`SHA256SUMS` and `SHA256SUMS.asc` from the v0.6.0 release's assets on GitHub
(`ZigboxOrg/zigbox`) into one directory, and in it run:

```sh
f=$(mktemp) && curl -fsSLo "$f" https://zigbox.org/zigbox-archive-keyring.gpg
test "$(gpg --show-keys --with-colons "$f" | awk -F: '$1=="pub"{n++;w=1} $1=="fpr"&&w{print $10;w=0} END{if(n!=1)print "BAD"}')" = 1207CB8600CE25FFDD3CC87ECCBEC141C3348787 \
  && gpgv --keyring "$f" SHA256SUMS.asc SHA256SUMS \
  && sha256sum -c --ignore-missing SHA256SUMS
rm -f "$f"
```

`gpgv` must print `Good signature from "Zigbox releases <releases@zigbox.org>"`, and
`sha256sum` `OK` for each tarball you downloaded. `SHA256SUMS` covers the Linux assets only; the
Mac zip is notarized and has its own `SHA256SUMS.macos`, with no gpg signature.

The subkey is renewed once a year; the keyring you install carries its expiry. When a release's
notes say it was renewed, fetch the keyring again with the same steps
([guide](../guide/try-linux.md), "Renewing the keyring").

## S2: lazy start

Slices 5 and 6 of S2 ([#169](https://github.com/Zigbox/zigbox/pull/169) before the move, then
[#8](https://github.com/ZigboxOrg/zigbox/pull/8) and [#16](https://github.com/ZigboxOrg/zigbox/pull/16);
[brief](../briefs/S2-lazy-start.md), the steps, cuts and risks in [docs/demos/s2.md](../demos/s2.md)).
Slices 1 to 4 were in 0.5.2 and 0.5.3, present but unreachable. In 0.6.0 every build has lazy
start: the `-Dlazy-start` build option and the E0004 refusal of `--lazy` are gone
([decision](../decisions/2026-11-18-0.6.0-lazy-start-gate.md),
[decision](../decisions/2026-11-21-lazy-on.md)).

- **`zbx run --lazy <image>`** mounts the image through a FUSE server in a user namespace and
  starts the command at once. A read of a file that is not local yet fetches its chunks by HTTP
  range from the registry, verifies each against the image's lazy index, and keeps it in the
  store. The image's record stays `partial` until every object is local. `--lazy` is opt-in;
  `zbx run` without it pulls the whole image first, as before. A library caller asks with
  `StartOptions.lazy`.
- **`zbx run -d --lazy` works.** The detached run's supervisor runs the FUSE server and tears it
  down (and wipes the registry token) after the container ends. `zbx exec` reads through the same
  mount, `zbx stop` ends it, and the lazy run's lines (W1202, E1203, E1206, E0417) and its summary
  go to the run's log, so `zbx logs` shows them.
- **Background fill** fetches the rest of the image after 2 s with no read
  (`lazy_fill_idle_ms`), in ranges of at most 2 MiB (`lazy_fill_range_bytes_max`), and yields to
  the container's reads ([decision](../decisions/2026-11-18-s2-fill-idle.md)). The run record is
  rewritten each second while the fetched bytes change (`lazy_progress_interval_ms`), so
  `zbx ps --output json` shows `lazy.local_percent` rising to 100; the image's record is rewritten
  whole once every object is local. `zbx store gc` during a fill keeps the partial image.
- **An image without a lazy index** (any image not pushed by 0.6.0's `zbx push`) still runs
  with `--lazy`: zbx warns (W1201, "the image has no lazy index: pulling it whole") and pulls it. `--lazy --rootfs` is refused (E1208).
- **`zbx doctor`'s `fuse` line** (new in 0.5.3) now describes a check `zbx run --lazy` needs:
  a warning (W1203) when FUSE cannot be mounted in a user namespace. A `/dev/fuse` that the user
  cannot open is now E1201, as a FUSE mount that fails is (it was E0205).
- **When a source fails:** a chunk whose bytes do not match its hash is a warning (W1202, naming
  the object and the chunk), and that source is not asked for that object again in the run; a
  read no source can serve fails with EIO in the container and E1203, retitled "a chunk could not
  be fetched: the read got EIO". With the registry down, a read that needs it gives up after
  `lazy_down_fail_ms` (2 s), and the registry is probed again every `lazy_down_probe_ms` (5 s). A
  full store fails the read with E1206.
- **A chunk the store keeps but cannot make into its object** (a failed generation bump, an
  `objects/` that cannot be written, EIO on the rename or sync, `security.capability` refused) is
  shown once per object as ZBX-E0417, whose cause names the step, the path under the store root
  and the kernel's reason; the read is still served from the kept chunk at once, and the source
  is not blamed ([decision](../decisions/2026-11-20-s2-held-failures-are-shown.md)).
- **Push and export write layer writer 2:** `zbx push`, `zbx push --dry-run` and
  `zbx store export` write the lazy index and the `org.zigbox.lazy-index` annotation, which
  `--lazy` needs. The library's `Input.writer_version` defaults to 2, and a caller can ask for 1.
  Every gzip reader reads writer 2 layers; see [Upgrading](#upgrading) for the digests.
- No codes were registered or removed. New bounds: `lazy_fill_idle_ms` (2,000),
  `lazy_fill_range_bytes_max` (2 MiB) and `lazy_progress_interval_ms` (1,000).

`demo-s2` runs the brief's nine steps in the VM as an ordinary user against a throttled
(40 MiB/s) registry and a 3 GiB image: the command ready in under 10 s with under 64 MiB fetched,
against a full pull of over 75 s; a detached run filled to 100 %; a v2 image that reuses the
store; a corrupted chunk refused; a registry outage and recovery; and the upgrade step from the
release before S2. Its status in CI is under the release gates below.

### S2: known limits

- **Rootless `--lazy`: files owned by an id other than root, and files with file capabilities,
  are never assembled: the image stays partial in `zbx ps` and a detached run rescans its
  catalogue every 5 s; reads are right and not delayed; fixed in 0.6.x.**
  ([decision](../decisions/2026-11-20-s2-rootless-owner-gap-accepted.md)). Running as root, or in
  a root-owned namespace with `CAP_CHOWN`, is not affected, and neither is a run without
  `--lazy`. This case shows no line.
- **ENOSPC while assembling a chunk that is already held** is treated as a full store: the read
  fails with EIO (E1206) and the fill pauses a round, although the kept chunk could have served
  it. The owner kept this behaviour for 0.6.0, and a test pins the order
  ([decision](../decisions/2026-11-20-s2-held-failures-are-shown.md), item 4).
- **An E0417 line can be lost.** When the lazy run's event queue is full, the `not_kept` event
  behind an E0417 line is dropped and counted in `events_dropped`; the run's summary counts it
  with the lines past `lazy_errors_shown_max`, but the line itself is never shown, and nothing
  reports it again (every chunk is held by then, so no later put meets the failure). The failure
  is still counted in the run record's `errors`. A store-wide cause can show one E0417 line per
  object, up to that bound.
- **An empty object made by the fill** (`land_empty`) turns a store failure into a failed fetch
  with no line at all, not an E0417. Known gap, same class as the one above.
- **W1202 and E1203 name the object, not the file's path.**
- **A source that sent wrong bytes for an object is not asked for it again for the rest of the
  run**, so a long-lived run whose registry sent one corrupt response cannot read that object
  until it restarts.
- **Right after the registry recovers**, a read can still get EIO for up to about 5 s, until the
  next probe (`lazy_down_probe_ms`) finds it answering.
- **The registry credential is resolved once per run.** A lazy run keeps the realm credential it
  started with and refreshes the registry's bearer token with it on a 401, but never asks for a
  new credential, so a run that outlives a short-lived credential (an ECR or Google access token)
  cannot fetch again.
- **A remote image whose `User` is a name, not a number, is refused with `--lazy` (E0521)**:
  the user database it would need is not fetched before the container starts. A numeric `User`
  or `--user 1000:1000` works. Registry fetches are serialized.
- **No test has an older `zbx` pull a writer 2 image.** 0.5.x's reader should read it (it stops
  at the first zero block and does not compare `diff_id` on a pull), but only `run -d` and `stop`
  across versions are tested.

## The move to ZigboxOrg

The repositories moved from `github.com/Zigbox` to `github.com/ZigboxOrg`
([#2](https://github.com/ZigboxOrg/zigbox/pull/2), [#11](https://github.com/ZigboxOrg/zigbox/pull/11),
[#13](https://github.com/ZigboxOrg/zigbox/pull/13)). For users:

- the issue link in an internal error (B0001) and `zbx explain` now names
  `github.com/ZigboxOrg/zigbox`;
- release tarballs, the SBOM and the Mac zip are on `ZigboxOrg/zigbox`'s releases, and the
  Homebrew formula is published to `ZigboxOrg/homebrew-tap`, which Homebrew names
  `zigboxorg/tap`: install with `brew install zigboxorg/tap/zigbox` (the old `zigbox/tap` is gone;
  see [Upgrading](#upgrading));
- the page every diagnostic links to (its `docs` line, the JSON `docs` field, `zbx explain`) is
  now `https://zigbox.org/errors/box/<code>.html`, no longer `https://zigbox.github.io/zigbox/errors/`.
  The old address, which 0.5.x prints, is not guaranteed: it answers today only from the old
  organisation's last Pages deployment, which nothing here keeps up. Every code's page, 0.5.x's
  included, is at `https://zigbox.org/errors/box/<code>.html`
  ([decision](../decisions/2026-11-21-error-docs-on-zigbox-org.md));
- the VM images and pinned packages the demos fetch are mirrored on `ZigboxOrg/zigbox` releases.

Links to runs, pull requests and releases from before the move still point at
`github.com/Zigbox`, as the records they are.

## The keeper and the OOM killer

- **An out-of-memory kill is reported as `oom` again** ([#6](https://github.com/ZigboxOrg/zigbox/pull/6),
  [decision](../decisions/2026-11-20-keeper-vfork-member.md)). A container killed by the OOM
  killer was sometimes reported as a plain SIGKILL (reason `signal`, exit 137): a second OOM in
  the scope killed the process that keeps the scope alive, systemd removed the scope, and its
  `memory.events` went with it. The keeper is now two processes: the keeper, outside the scope,
  and a vfork child of it, the only one in the scope, which the kernel never picks as an OOM
  victim.
- **The keeper takes two of the user's processes**, not one, outside the scope (two of
  `RLIMIT_NPROC` and of the parent cgroup's `pids.max`). `TasksMax` is unchanged (`--pids` plus
  one). A user one process short of the limit is refused with ZBX-E0205, whose cause is the
  kernel's EAGAIN.
- **E0205 says how the keeper ended** ([#9](https://github.com/ZigboxOrg/zigbox/pull/9),
  [#17](https://github.com/ZigboxOrg/zigbox/pull/17)): "exited with status N before it was
  ready" or "killed by signal N before it was ready" (SIGKILL is usually the OOM killer or a
  user's kill). The keeper re-raises its member's signal, so a signal is never reported as exit
  status 1. zbx's wait for the keeper is bounded (`keeper_waits_max`, 4,096), and the member runs
  on a 64 KiB stack (`keeper_stack_bytes`).

  setup scripts) are new; neither is part of the package.

## Upgrading

0.6.0 reads every store, record and lock 0.5.3 wrote. Upgrade every `zbx` that shares a store
together, and Zigcube's agent with them. First replace the release key
([above](#the-new-release-key)), or `apt update` and `dnf` refuse 0.6.0.

- **New digests from push and export.** The same tree pushed or exported by 0.6.0 gets new layer
  and manifest digests compared with 0.5.x, because they are layer writer 2. A pipeline that
  compares a pushed digest against one recorded by 0.5.x sees a change once. Images already in a
  registry, and what `zbx pull` stores from them, do not change.
- **Run records:** a detached `--lazy` run writes run record version 11, which 0.5.3 reads. A
  `zbx` before 0.5.3 does not know version 11: v0.5.1 (tested in demo-s2) leaves such a run out
  of `zbx ps --all` without a word and refuses to `stop` it (E0402, "from a newer zbx"). Any other
  run writes the version 0.5.3 would have.
- **Image records:** a lazy run's image is recorded as `partial` (image record version 4), which
  0.5.3 reads; whole images stay version 3.
- **Containers started by 0.5.3 keep running** and are listed and stopped by 0.6.0. Their keeper
  is the single process of 0.5.3 until they are restarted.
- **On a Mac, switch taps.** The Homebrew tap moved to `zigboxorg/tap`. The old tap's
  repository, `zigbox/homebrew-tap`, is gone, so `brew update` and `brew upgrade` can no longer
  reach it, and a Mac that installed from it stays on 0.5.x. Remove the old install and the old
  tap, then install from the new tap:

  ```sh
  brew uninstall zigbox
  brew untap zigbox/tap
  brew install zigboxorg/tap/zigbox
  ```

  `brew uninstall` removes only what brew installed, the `zbx` binary; the files zbx made under
  `~/Library/Application Support/zbx` (the store among them) are not brew's and are kept.

- **M6d is still not demonstrated.** `demo-m6d` needs the owner's Google setup
  ([docs/demos/m6d.md](../demos/m6d.md)) and still prints `NOT RUN` in CI; 0.5.3 moved its live
  demo to 0.6.0, and it has not run (release gates below). Artifact Registry's answer for a
  missing repository is still unverified ([decision](../decisions/2026-11-16-m6d-missing-repo-unverified.md)).
- **The S2 limits** above.
- **Carried over from 0.5.3, not fixed:**
  - A Google token realm is checked for the registry's host but not its port.
  - E0567's fix ("get a new access token") fits a library caller; on the command line zbx gets the
    token itself.
  - `zbx gc` under-reports the bytes it frees from a partly fetched object with more entries than
    its listing holds; removal is unaffected.
  - The top-level help line for `doctor` does not mention `--require-host`.
  - `--ulimit` refuses a value of more than 18 digits that a u64 holds.
  - `zbx exec` does not get the container's `--ulimit`; `--ulimit nproc` counts the invoking
    user's own processes; a sysctl written later inside the container wins; `pids.max` inside
    reads `--pids` plus one; the cgroup view does not help a runtime that ignores it.
- The known issues of [0.5.2](0.5.2.md) are unchanged; the guide ([docs/guide/](../guide/index.md))
  does not cover M9, M10, C4, M2b, M6d or S2.
