# S2: the lazy resolver writes owners as host ids

*Decided 2026-11-18, by the slice (S2 slice 6 fix, the demo-s2 stalls). Open for the supervisor: the gap below.*

**The bug.** The lazy resolver's slots are threads, so they run in `zbx run --lazy`'s parent, outside the store's namespace (`store/owners.zig`, Z9). A put that completes an object (`chunks.put_chunk` → `assemble` → `build_file` → `object.apply`) changed the new file's owner to the container's ids with `fchown`. Rootless, `fchown(fd, 0, 0)` is `EPERM`, so every such put failed (`land` → `.failed`). A trace of demo-s2 in the VM (scratch run 44370517375) showed it: every on-demand fetch of a one-chunk object, and of boot.bin's last chunk, ended `failed` with all its bytes sent. Its chunk stayed in `partial/`, so the retry a round later (`lazy_down_fail_ms`, 2 s) found it local. Four such reads at about 2 s each made the 10.8 s lazy start (step 2). The fill never made an object whole: step 4 counted 0 whole objects, and every one-chunk object it fetched failed, one every 5 s. The trace showed no `store_full` at all, so the free-space floor was not involved.

**Decision.** `object.apply` takes the store's `owners`. Inside the namespace nothing changes. Outside, each container id is mapped to its host id (`owners.host_of`, the inverse of `container_id`). When that is the user's own uid and gid (container root), there is no `fchown`: this process just created the file, so it already has that owner. Any other id is passed to `fchown` as its host id, and the kernel decides: root (`CAP_CHOWN`) succeeds, and a plain user gets `EPERM`, as before. An id the map does not reach fails the put with `AccessDenied`.

**The gap, not fixed here.** Rootless, an object owned by any container id but root (for example `etc/shadow`, 0:42), or one carrying `security.capability`, still cannot be completed from outside. Its reads are served from `partial/` a round late, and the fill retries it on every pass. Closing it needs the completion done inside the namespace: per Z6 and Z9, a single-threaded store child that assembles objects (or receives them over a pipe) with `owners` `.inside`. That is a design change for the supervisor.

**Review of the slice (2026-11-20), still open for the supervisor.** The review (PR 8) made the gap a MUST: rootless, `zbx run -d --lazy alpine:3.20` never makes `/etc/shadow` (0:42) an object. Every chunk is held and verified in `partial/`, so reads are served, but the object is never assembled, the fill retries it each pass, and the record stays partial. `chunks_tests.zig` ("outside the namespace an object of a container id but root is held, not made, until finished inside") pins this: the last put fails, the chunks stay, and `chunks.finish` with `owners` `.inside` makes the object from them with nothing fetched again. A `security.capability` xattr fails the same way for the same reason (the kernel gives `CAP_SETFCAP` only inside the namespace). Options, none built:

1. **A finishing pass inside the namespace.** At the end of the fill, and when a lazy run ends, `zbx` re-execs itself (a fresh single-threaded process, as `store/namespace.zig` asks of a worker) to run `chunks.finish` for every object whose chunks are all held, then `record_whole`. Needs: a hidden command or mode, the list of held objects handed over, a test in a real rootless VM with a subordinate range (the demo's fixture is all root's; it needs a 0:42 file and a file with `security.capability`), and a way to tell the user it is running. It also adds a process to every exit path of a detached run. Largest, and the one that makes the image whole.
2. **Treat a record as whole when every chunk is local.** Cheap, but `whole` then no longer means the objects are in `objects/`: a run without `--lazy` uses the farm, which needs them. It would have to assemble first, which is option 1.
3. **Stop the retrying, keep the image partial.** The resolver marks an object whose put failed on its owner as needing the namespace, serves its reads from `partial/` at once (no `lazy_down_fail_ms` round) and the fill skips it. The image stays partial for good, and a later `zbx pull` of it, which runs in the namespace, makes it whole. Contained in `land.zig` and the schedule, but changes what `ps` shows (never 100 %).
4. **Accept and record it** for 0.6.0 with a line in the release text.

Nothing here is built; the slice records the gap under "Cuts and deviations" in docs/demos/s2.md.
