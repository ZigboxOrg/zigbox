# S2: a held chunk whose object cannot be made is shown, unless it is the rootless owner gap

*Decided 2026-11-20, by the slice (the follow-ups of the second re-review of PR 8). Supersedes in part [2026-11-20-s2-rootless-owner-gap-accepted.md](2026-11-20-s2-rootless-owner-gap-accepted.md) and [2026-11-18-s2-lazy-owner-outside.md](2026-11-18-s2-lazy-owner-outside.md).*

**1. `Landed.held` is wider than the owner gap.** It is returned for every failed put that left a verified chunk in `partial/`: the owner refusal, but also a failed generation bump, an `objects/` that cannot be created or written (EACCES, EROFS), EIO on the rename or the sync, an EPERM from setting `security.capability` (rootless, no `CAP_SETFCAP`) or from a create or rename in an immutable or sticky directory, and the lock file. Booking these as the source's answer is right, but they were silent: the object never completes, the fill rescans, and the operator saw no line. Now `land` fills in the failure, and every store failure of a chunked put names its step (`fs.Failure.step`: the lock, the look, the chunk's read and write, the listing, the generation, the directory, the create, the assembly's reads and writes, the owner, the mode, an xattr, the time, the chunk list, the rename, the sync). `land.owner_refused` names the one accepted case: the step is `owner`, marked where `object.apply_owner` refuses (an id the map cannot show, `AccessDenied` with no errno, or EPERM from `fchown`). The errno alone never decides it, so an EPERM from any other step is shown. For any other `held` the resolver queues one `Event.Kind.not_kept` per object, shown as ZBX-E0417 ("can't write the store"; its explanation covers permissions, a read-only file system and an I/O error). Its cause names the step and its path relative to the store root (`objects/<shard>`, `partial/`, `tmp/`, the generation or lock file) and the kernel's reason, as E0417's explanation promises ("The cause names the path"); `src/lazy_lines.zig` has the rendered line. No new code is registered and the registry text is unchanged. The rootless owner gap stays silent, as the owner accepted.

The event is reported once per object, not once per run or per cause: a store-wide cause (the generation file, the lock) can show one line per object, up to the lazy run's lines bound (`lazy_errors_shown_max`), past which lines are counted, not shown. Changing that is a change to a user-visible bound, so it is left for a decision of its own. The failure is counted in the run record's `errors` whether or not its event is queued, as a full store and a refused read are. When the event queue is full the event is dropped and counted in `events_dropped`, the same as every other kind, and the drop is final: the failure almost always comes from the assembly at the last missing chunk's put, after which every chunk is held, reads are served from `partial/` and nothing puts a chunk of the object again, so no later put meets the failure to report it. The run's summary counts the dropped line with the lines past the bound; the line itself is lost. Retrying a dropped report is not built.

`land_empty` (an empty object, made by the fill, not by a read) still turns a store failure into `.failed` without a line. Reporting it needs a path from the fill's plan to the schedule for an object with no chunk, which is more than this change; it is a known gap, recorded here, of the same class.

**2. Corrections to the records this replaces.**
- 2026-11-20-s2-rootless-owner-gap-accepted.md says the new test "fails on 3834fe77: the fifth read is `Unavailable`". It fails at the first read (index 0): on that commit the read needs a round and gets `.wait`. The fifth read is at 28.4 s, under `lazy_read_deadline_ms` (30 s), so the loop never reaches the mark-down; the asserts after it (not down, no `failing_since_ms`, no `unavailable` event) are what catch a source booked as failing.
- 2026-11-18-s2-lazy-owner-outside.md says reads are served "a round late" and that "the fill retries it on every pass". Both are superseded: reads of a held chunk are served at once, and the fill rescans, it does not retry the put. The gap stays accepted for 0.6.0 (2026-11-20-s2-rootless-owner-gap-accepted.md).

**3. `land` always fills `failure`.** `chunks.held_count` fails with `StoreFailed` without filling the caller's failure, so the one `land` read (`failure_is_full`) was uninitialised memory on that path. `land` now sets it to `IoFailed`, errno 0, before the put, and the listing fills it like every other step. A failure with no errno names the error's class in E0417's cause ("permission denied"), or, for `IoFailed`, says "the store gave no reason"; it never guesses an errno. The assembly's rename also recorded its errno after the cleanup's `unlink`, which overwrote it (errno 0); it is now recorded first.

**4. ENOSPC on a chunk that is already held: a known limit for 0.6.0, kept.** `land` checks `failure_is_full` before `is_held`, so an ENOSPC while assembling a held chunk is `.store_full`: the read fails (E1206, EIO) and the fill pauses a round, although the held chunk could serve it. Putting `is_held` first would serve the read and stop the E1206, but it would change what a user sees on a full disk (a read that fails would succeed, and the fill would stop pausing). The owner decided to keep today's behaviour for 0.6.0; a test in `src/lazy/resolver_test.zig` pins the order, and stays until that is changed on purpose.
