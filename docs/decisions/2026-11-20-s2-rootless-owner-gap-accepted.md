# S2: the rootless owner gap is accepted for 0.6.0, and `lazy_down_fail_ms` stays 2 s

*Decided 2026-11-20, by the owner (in writing to the supervisor, on the review of PR 8).*

**1. The gap is accepted for 0.6.0 as a recorded cut.** Review of S2 slice 6 (MUST 2, `src/store/object.zig` `apply_owner`): the lazy resolver's slots are threads, so they run outside the store's namespace (`store/owners.zig`, Z9). Rootless, a file's owner can only be changed to the user's own ids there, and `fchown` to any other id, or a `security.capability` xattr, is `EPERM`. Scenario: rootless `zbx run -d --lazy alpine:3.20`. `/etc/shadow` is 0:42, so the put of its last chunk fails; every chunk stays held and verified in `partial/`, the object is never assembled, the run's record stays `partial`. (As first written this also said the fill retries the object and each read waits a round; see the correction below.)

**Correction (fix on the re-review of PR 8, same day).** The first text of this decision said a read of such a chunk waits `lazy_down_fail_ms` for a round and that the fill retries the object. Both were wrong, and the first hid a worse effect. The failed put came back from `land` as `failed`, and the schedule books `failed` against the source's health: after `lazy_read_deadline_ms` of such puts an honest registry or peer was marked down, reads failed `Unavailable` (EIO in the container) and E1203 blamed the source, even for chunks already held. Now `land` tells a put that failed after keeping a verified chunk (`Landed.held`) from one that lost it, and the resolver books it as the source's answer (`landed`): the bytes were right. The source is never marked down for it, no E1203 is logged, and the read is served from `partial/` in the same round, with no wait. Test: `src/lazy/resolver_test.zig`, "an owner failure is never the source's failure, over many reads" (five 0:42 objects read over 35 s of simulated time; it fails on 3834fe77: the fifth read is `Unavailable`, the peer is down). `lazy_down_fail_ms` is unchanged.

What users see: the run works and every read returns the right bytes at once. Files owned by any id but container root (and files with `security.capability`) are never assembled into objects, so `zbx ps` never shows the image 100 % local and the record stays `partial`. The fill never reaches `done` for the life of a detached run: held chunks are local, so it fetches nothing, but it rescans the catalogue (an `lstat` per object, and one per chunk of every object that is not whole, under the store lock) every `lazy_down_probe_ms`. Running as root, or in a root-owned namespace with `CAP_CHOWN`, is not affected; neither is a run without `--lazy`.

`src/lazy/resolver_test.zig` ("rootless, an object owned by a container id is never made whole") pins this with the simulated file system, with a subordinate range and the owner gate (it asserts the gate's call count), and `src/store/chunks_tests.zig` pins that the held chunks finish inside the namespace with nothing fetched again. The `security.capability` case has no gate in `SimFs` and is not tested.

**Follow-up (0.6.x).** Complete the object inside the user namespace, as [2026-11-18-s2-lazy-owner-outside.md](2026-11-18-s2-lazy-owner-outside.md) proposes (its option 1: a finishing pass in a fresh single-threaded `zbx` process that runs `chunks.finish` for every object whose chunks are all held), with a rootless VM test whose fixture has a 0:42 file and a `security.capability` file. Until then the cut is recorded in `docs/demos/s2.md`, "Cuts and deviations".

**Release text.** `docs/releases/0.6.0.md` does not exist on this branch, so it is not edited here. The 0.6.0 RC1 release notes must carry a "Known limits" line: "Rootless `--lazy`: files owned by an id other than root, and files with file capabilities, are never assembled: the image stays partial in `zbx ps` and a detached run rescans its catalogue every 5 s; reads are right and not delayed; fixed in 0.6.x."

**2. `lazy_down_fail_ms` stays 2000 ms.** No change to the constant.
